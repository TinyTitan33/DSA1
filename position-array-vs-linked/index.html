Key takeaway: Neither structure wins everywhere. The array must shift every item after the gap (n − i elements), so adding at the end is cheap (O(1), while there is room) but adding at the front is expensive (O(n)). The linked list must walk from the head to the gap (i hops), so adding at the front is cheap (O(1)) but adding at the end is expensive (O(n)). Re-pointing the two arrows is always constant time; the walk is where the linked list spends its effort.

Notice: the two numbers always add up to n. No position is cheap for both, and in the middle each side costs about n/2, however long the list is. That is what O(n) means here.

This counts operations, not time. Copying neighbouring array elements is a fast block copy, while following links from node to node is often slower per step, so an array can win even where the counts look level. Also, Java’s java.util.LinkedList is doubly linked and keeps a tail reference, so adding at either end is O(1). The picture above is the simplest version.
